                        PROGETTO GATTILE - DESCRIZIONE PROGETTUALE

TITOLO: Sistema Integrato per Gestione Adozioni e Volontariato in Gattile

================================================================================
1. VISION E SCOPO
================================================================================

Il progetto Gattile è un'applicazione web full-stack sviluppata per facilitare le
adozioni di gatti e l'organizzazione del volontariato presso una struttura di
accoglienza felina. L'applicazione rispetta rigorosamente i principi di 
accessibilità, usabilità, sicurezza e performance.

================================================================================
2. STACK TECNOLOGICO E SCELTE PROGETTUALI
================================================================================

2.1 BACKEND - PHP
------------------
- Versione: PHP 7.4+
- Approccio: Orientato agli oggetti e funzionale (stile procedural)
- Pattern: MVC-like con separazione tra logica di business e presentazione
- Template: Mixed PHP + HTML semantico
- Comunicazione: REST API JSON per Frontend e Ajax

MOTIVAZIONE: PHP è stato scelto per la sua ampia disponibilità negli ambienti
di hosting condivisi e per la facilità di integrazione con database relazionali.
La separazione tra includes, api e pagine permette modularità e riutilizzo del
codice.

2.2 DATABASE - MySQL/MariaDB
------------------------------
- Versione: 5.7+
- Charset: UTF-8 MB4 (supporto emoji e caratteri speciali)
- Transactions: Supportate per operazioni critiche
- Stored Procedures: Non utilizzate (logica nel PHP)

SCHEMA:
  - utenti: Gestione profili con ruoli (admin/user)
  - gatti: Catalogo animali con metadati
  - prenotazioni_visite: Prenotazioni visite conoscitive
  - visita_gatti: Relazione many-to-many (prenotazione <-> gatti)
  - turni_volontariato: Turni volontariato con vincolo di slot

SECURITY:
  - Prepared Statements: Contro SQL injection
  - Password Hashing: BCrypt con cost=12
  - Foreign Keys: Vincoli referenziali con ON DELETE CASCADE
  - Indici: Su campi di ricerca/join frequenti (username, data_arrivo, nome)

PRIVILEGE SEGREGATION (Least Privilege Principle):
  - 'lecture': SELECT only
    Usato per: Lettura gatti, disponibilità slot, lettura prenotazioni
  
  - 'modifier': SELECT, INSERT, UPDATE
    Usato per: Creazione prenotazioni, inserimento gatti, booking visite
  
  - 'registrator': INSERT only (su utenti)
    Usato per: Registrazione nuovi utenti
    Scopo: Contenere breach se account compromesso

NOTA: L'utente 'admin' di sistema NON è mai usato (best practice OWASP).

2.3 FRONTEND - HTML5 SEMANTICO
--------------------------------
- Markup: Esclusivamente tag semantici (header, nav, main, article, section,
  aside, footer, figure, figcaption, progress, meter)
- NO divs/spans: Utilizzati solo dove strutturalmente necessario (raramente)
- DOCTYPE: HTML5 DOCTYPE
- Charset: UTF-8 esplicito
- Viewport: Responsive meta tag

MOTIVAZIONE:
  - Tag semantici migliorano SEO e accessibilità screen reader
  - Favoriscono la comprensione della struttura logica
  - Facilitano styling CSS e automat azione test
  - Supportano meglio la navigazione vocale

2.5 JAVASCRIPT VANILLA - FORM VALIDATION
--------------------------------------------

MODULO FormValidator:
  - Namespace pattern (IIFE) per evitare inquinamento globale
  - Non usa jQuery o dipendenze esterne
  - Validazione client-side in tempo reale (debounced a 300ms)
  - Regole personalizzabili tramite API

FEATURE:
  - Real-time validation (blur, input, change events)
  - Messaggi di errore inline con ARIA live regions
  - Supporto regex e custom validators
  - Popola/Reset form da dati
  - Disable submit durante elaborazione
  - Correlazione tra campi (es: password confirm)

REGOLE IMPLEMENTATE:
  - username: /^[a-zA-Z][a-zA-Z0-9_-]{3,49}$/
    (inizia con lettera, 4-50 caratteri)
  
  - password: /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[@$!%*?&])[A-Za-z\d@$!%*?&]{8,16}$/
    (maiuscola, minuscola, numero, simbolo, 8-16 caratteri)
  
  - email: /^[^\s@]+@[^\s@]+\.[^\s@]+$/
  
  - nome/cognome: /^[a-zA-ZàèéìòùÀÈÉÌÒÙ\s]{2,50}$/
    (lettere italiane, 2-50 caratteri)
  
  - indirizzo: 5-100 caratteri
  
  - data_arrivo: deve essere <= oggi

2.6 REACT.JS - COMPONENTE GALLERIA GATTI
-------------------------------------------

ARCHITETTURA:
  - Componente: CatsGallery (unico componente React)
  - Libreria CDN: React 18 + Babel standalone
  - Utilizzo: Visualizzazione, ordinamento, filtro gatti
  - State: cats[], filteredCats[], selectedCats[], loading, error

FEATURE:
  - Fetch API: Carica dati da /api/gatti-api.php
  - Ricerca: Filtro per nome/descrizione (case-insensitive)
  - Ordinamento: per data_arrivo, eta, nome, colore_mantello
  - Selezione: Checkbox per utenti autenticati
  - Paginazione: Non implementata (mostra tutti)

COMUNICAZIONE CON VANILLA JS:
  - CustomEvent: 'catsSelected' inviato su document
  - Detail contiene: selectedCatIds[], selectedCatsData[]
  - Form Vanilla JS ascolta evento e aggiorna UI

MOTIVAZIONE SCELTA REACT:
  - Esigenza specifica del progetto (requirement)
  - Dimostra competenze architetturali multi-framework
  - Virtual DOM efficiente per lista lunga
  - Separazione logica presentation da data fetching

2.7 COMUNICAZIONE FRONTEND-BACKEND
-----------------------------------

MODELLO 1: Form tradizionale PHP (Login, Registrazione)
  - POST form a PHP
  - Validation lato client (JS) + server (PHP)
  - Redirect su successo
  - Validazione server indipendente e mandatory

MODELLO 2: AJAX/Fetch (Gatti, Prenotazioni, Volontariato)
  - Content-Type: application/json
  - Request/Response JSON
  - No page reload
  - Error handling client-side con aria-live

MODELLO 3: CustomEvent (React -> Vanilla JS)
  - Evento inviato su document quando selezionati gatti
  - Form ascolta con addEventListener
  - Decoupling tra componente React e form
  - Evita props drilling e prop inversion

API REST ENDPOINTS:
  /api/gatti-api.php
    GET ?action=all&search=&sort=data_arrivo&order=DESC
    GET ?action=latest&limit=2
    GET ?action=detail&id=1
    GET ?action=count
  
  /api/booking-api.php
    POST {visit_date, visit_time, cat_ids}

    DELETE {booking_id}

2.8 SESSIONI E AUTENTICAZIONE
-------------------------------

COOKIE DI SESSIONE:
  - Nome: PHPSESSID (default PHP)
  - Lifetime: Fino alla chiusura browser
  - Secure: true (HTTPS only)
  - HttpOnly: true (no JS access)
  - SameSite: Strict (protezione CSRF)

REMEMBER-ME TOKEN:
  - Persistenza: 72 ore
  - Meccanismo: Cookie + file JSON (in produzione: DB)
  - Token: Opaco (hash SHA-256 di random bytes)
  - Credenziali: NON salvate in chiaro
  - Autenticazione: Sempre via sessione PHP + password verify
  - File: /data/remember_tokens.json (writable by web server)

FLUSSO AUTENTICAZIONE:
  1. User submit login + "remember me"
  2. Server verifica password con password_verify()
  3. Se OK: crea SESSION + opzionalmente token cookie
  4. Successivi accessi: controlla token, pre-compila username (password vuota)
  5. Accesso effettivo sempre richiede password
  6. Logout: cancella SESSION + cookie token

2.12 SICUREZZA - OWASP GUIDELINES
----------------------------------

A1 - INJECTION:
  - Prepared statements su tutte le query
  - HTML escaping output: htmlspecialchars()
  - stripstags() su input non permesso

A2 - BROKEN AUTHENTICATION:
  - Password hashing: BCrypt cost=12
  - Session timeout: 30 minuti inattività
  - Remember-me token opaco (non credenziali)
  - HTTPS-only cookies

A3 - SENSITIVE DATA EXPOSURE:
  - Niente credenziali in cookie/localStorage
  - JSON response non contiene password
  - Errori non rivelano dettagli DB

A7 - CROSS-SITE SCRIPTING (XSS):
  - Output encoding: htmlspecialchars() su tutti i dati user
  - Content-Security-Policy header
  - InputType: text/email/number (HTML5 validation)

A9 - USING COMPONENTS WITH KNOWN VULNERABILITIES:
  - Dipendenze minimali (React CDN, Babel standalone)
  - Niente npm dependencies (no node_modules attack surface)

ADDITIONAL:
  - CSRF: SameSite=Strict cookie
  - SQL Injection: Prepared statements
  - Command Injection: Non esecuzione shell
  - Security Headers: X-Content-Type-Options: nosniff

4. DECISIONI PROGETTUALI CRITICHE
================================================================================

4.1 PERCHÉ REACT + VANILLA JS INSIEME?
  - React fornisce UI reattiva efficiente per lista gatti
  - Vanilla JS forma è più semplice, leggero e direct control
  - Communication tramite CustomEvent è decoupled, testabile
  - Dimostra capacità integrare multiple tecnologie
  - Riduce dipendenze totali (no Redux, no routing lib)

4.2 PERCHÉ FILE JSON PER REMEMBER TOKENS?
  - Produzione userebbe DB (turni_volontariato table)
  - JSON è semplice, leggibile, versionabile
  - Alternative: memcached/Redis non sempre disponibili
  - Pulisce token scaduti automaticamente

4.3 PERCHÉ 3 UTENTI DB?
  - Least Privilege Principle (OWASP)
  - Breach singolo account limita danno
  - registrator: può solo creare utenti, non modificare
  - lecture: read-only per query pubbliche
  - modifier: modifica dove necessario

4.4 PERCHÉ NO FRAMEWORK (Laravel, Symfony)?
  - Requêtes: PHP puro + MySQL
  - Frameworks overkill per progetto piccolo
  - Più controllo su security + performance
  - Facilita debugging + learning

4.5 PERCHÉ CSS-IN-HTML (style tag)?
  - Piccolo progetto: singolo file CSS più semplice
  - Niente build step necessario
  - CSS variables garantisce consistenza
  - Media queries all'interno del file
  - Alternativa: separate file.css (implementato)

4.6 PERCHÉ NO PAGINATION?
  - Assunzione: pochi gatti (< 100)
  - Carico query minimo
  - Future: aggiungere LIMIT con offset

4.7 PERCHÉ NO EDIT/DELETE GATTI?
  - Requirement: solo INSERT gatti (admin)
  - Modifica futura: implementare PUT/DELETE su API
